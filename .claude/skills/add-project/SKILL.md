포트폴리오 프로젝트 데이터를 추가하거나 수정합니다.

아래 형식의 raw 텍스트를 파싱해 `src/data/portfolio-projects.json`에 구조화된 데이터로 저장합니다.

## 데이터 스키마

```typescript
interface PortfolioProject {
  id: string; // 영문 kebab-case (프로젝트명 기반)
  title: string; // 프로젝트 이름
  type: "side" | "work"; // "side": 사이드 프로젝트, 개인 프로젝트 | "work"
  period: {
    start: string; // "YYYY.MM"
    end: string; // "YYYY.MM" | "present"
  };
  role: string; // 실제 담당 역할 범위를 구체적으로 (예: "기획 · 디자인 · 프론트엔드 개발")
  tags: string[]; // 기술 스택
  summary: string; // 카드에 표시할 한 줄 소개 (1문장, 30자 내외)
  problem: string; // 문제 인식: 무엇이 불편했고 왜 문제라고 봤나 (1~2문장)
  approach: string; // 문제 접근: 어떤 가설·관점·설계 방향으로 풀려 했나 (1~2문장)
  solution: string[]; // 문제 해결: 실제로 만든 것과 그 결과/의미 (행동 + 결과 항목, 3~5개)
  takeaway: string; // 이 프로젝트가 드러내는 나의 역량·특성·관점 (1~2문장)
  image?: string; // 카드에 표시할 이미지 URL (선택)
  color: string; // Tailwind gradient (예: "from-purple-500 to-pink-500")
  size: "large" | "medium" | "wide" | "tall"; // 벤토 그리드 카드 크기
  links: {
    demo?: string;
    code?: string;
  };
}
```

### 본문 구조 선택 (중요)

프로젝트 본문은 **두 가지 작성 구조** 중 하나를 고른다. 렌더링 코드(`src/data/projects.tsx`, `$projectId.tsx`)가 둘 다 지원하며, 어느 쪽이든 `summary`/`takeaway`는 공통이다.

**① 단일 아크 (기본값)** — 위 스키마의 `problem`/`approach`/`solution`. 하나의 핵심 문제의식에서 출발한 프로젝트에 쓴다. 사이드 프로젝트나 단일 테마 프로젝트 대부분이 여기 해당.

**② 다중 테마 아크** — 서로 **독립된 문제를 여러 개** 풀어낸 프로젝트(주로 규모 있는 `work` 프로젝트)에 쓴다. `problem`/`approach`/`solution` 대신 다음을 사용:

```typescript
themes: {
  title: string;    // 테마 제목 (예: "수천 셀의 렌더링 성능")
  problem: string;  // 이 테마의 문제 인식 (1~2문장)
  approach: string; // 이 테마의 접근 (1~2문장)
  solution: string; // 이 테마의 해결 + 결과 (1~2문장)
}[]; // 테마 2~3개 권장
```

이 구조는 별도의 `overview`를 두지 않는다. 프로젝트 전체 맥락(여러 테마를 묶는 큰 줄기)은 `summary`가 한 줄로 잡아주고, 본문은 곧바로 테마 카드로 들어간다.

**판단 기준:** "이 프로젝트가 푼 문제가 하나인가, 여러 갈래인가?" 단일 가설·단일 테마면 ①, 성능·확장성·보안처럼 **성격이 다른 문제를 각각 다른 판단으로** 풀었다면 ②. 억지로 ②로 쪼개면 테마마다 problem/approach가 전체 서술과 겹쳐 분량만 늘어나니, 진짜 독립된 문제일 때만 사용한다.

**③ 구버전 (신규 작성 금지)** — 기존 데이터 일부는 구버전 스키마(`overview: string` + `keyContributions: string[]`)를 쓴다. 해당 항목의 다른 필드만 수정할 때는 구조를 보존하고, 사용자가 명시적으로 요청한 경우에만 ①/②로 전환한다.

## 작업 순서

1. `src/data/portfolio-projects.json` 파일을 읽는다 (없으면 빈 배열 `[]`로 시작)
2. `$ARGUMENTS`의 raw 텍스트를 파싱해 스키마에 맞게 구조화한다
   - `id`: 프로젝트 제목을 영문으로 변환한 kebab-case
   - `type`: 사이드 프로젝트 → `"side"`, 회사 업무 → `"work"`
   - `role`: 실제 담당한 역할 전체를 나열 (단순 "개발"보다 구체적으로)
   - `color`: 프로젝트 분위기·도메인에 어울리는 Tailwind gradient 조합을 임의로 선정
   - `size`: 프로젝트 규모·중요도를 고려해 임의로 선정 (`large` > `wide`/`tall` > `medium`)
   - `summary`, `problem`, `approach`, `solution`, `takeaway`: 아래 **콘텐츠 작성 원칙** 참고
3. 동일 `id`가 존재하면 덮어쓰고, 없으면 배열에 추가
4. period 비교 후 시간순으로 내림차순 정렬
5. 파일을 저장한다
6. 추가/수정된 항목의 핵심 내용을 요약해서 보여준다

## 콘텐츠 작성 원칙

입력 텍스트를 그대로 옮기지 말고, 포트폴리오 독자(채용 담당자, 동료 개발자)에게 인상을 남길 수 있도록 **내용을 풍부하게 확장**한다. AI 가 작성한 것 같은 느낌을 최대한 줄이고 딱딱한 느낌을 없앤다. 문체는 "~했음" / "~하였음" 형태를 기본으로 한다 ("~했다", "~하였다" 사용 금지). 단, "~를 적용", "~를 개선", "~를 구현"처럼 명사형으로 끝내도 자연스러운 경우에는 "했음"을 붙이지 않는다.

### Summary

- 프로젝트의 도입부 소개. **홈 카드**(길면 3줄로 잘려 노출)와 **상세 페이지 헤더**(전문 노출)에서 함께 쓰인다
- 길이에 정답은 없다. 단일 아크(①)·구버전(③)은 "왜 만들었나/무엇을 해결했나"를 압축한 **한 줄("~ 한 프로젝트")**이 잘 맞고, 다중 테마(②)는 별도 overview가 없으므로 **여러 테마를 묶는 맥락을 1~2문장**으로 담는다
- 핵심은 첫 문장만 읽어도 프로젝트가 무엇인지 잡히게 하는 것 (카드에서 잘릴 수 있으므로 앞부분에 핵심을 둔다)

**`problem` → `approach` → `solution`은 하나의 서사로 이어진다.** 읽는 사람이 위에서 아래로 내려가며 "이런 문제가 있었고(problem), 이렇게 접근해서(approach), 이렇게 풀었구나(solution)"를 자연스럽게 따라갈 수 있도록 세 필드를 연결해서 작성한다. 각 필드는 다음 단계로 매끄럽게 넘어가야 하며, 같은 내용을 반복하지 않는다.

다중 테마 구조(②)에서는 **각 테마가 이 서사를 독립적으로** 갖는다. 테마별 `solution`은 배열이 아니라 1~2문장 서술이며, 아래 Problem/Approach/Solution 원칙을 테마 단위로 그대로 적용한다. 여러 테마를 묶는 전체 맥락은 별도 필드 없이 `summary` 한 줄이 담당한다.

### Problem (문제 인식)

- **무엇이 불편했고, 왜 그것을 문제로 봤는지**를 구체적으로 서술한다
- 기존 솔루션의 한계나 불만족 지점을 짚으면 동기가 명확해진다
- "무엇을 만들었다"가 아니라 "무엇이 문제였나"에 초점. 해결책은 아직 꺼내지 않는다
- 1~2문장

### Approach (문제 접근)

- 그 문제를 **어떤 가설·관점으로 바라봤고, 어떤 방향의 설계 결정을 내렸는지**를 담는다
- 구체적인 구현 나열이 아니라 "왜 그렇게 접근했나"라는 전략·판단에 초점
- problem에서 제기한 문제를 받아 자연스럽게 해결의 방향으로 이어준다
- 1~2문장

### Solution (문제 해결)

- approach에서 정한 방향을 **실제로 어떻게 구현했고 그 결과/의미는 무엇인지**를 항목으로 나열한다
- 각 항목은 **행동 + 결과/의미**로 구성한다. 명사형으로 끝낼 수 있으면 그대로 사용하고 ("~를 적용해 성능 개선", "~를 구현"), 동사형 서술이 필요한 경우 "~했음" 형태로 마무리한다 ("~함으로써 ~를 달성했음")
- 기술적 구현뿐 아니라 UX·기획·디자인 등 기여의 범위도 드러낸다
- 입력에 명시되지 않았더라도 맥락상 자연스럽게 유추되는 기여는 추가할 수 있다
- 항목 수는 3~5개 권장

### Takeaway

- 이 프로젝트가 **나라는 사람의 어떤 면**을 보여주는지 서술한다
- 단순 기술 습득 요약이 아닌, 사고방식·태도·관점·역량을 언급한다
- 1~2문장

$ARGUMENTS
